# USBIP: восстановление после задержек — 2026-10-15

Подготовлена новая сборка `outputs/xone-probe.exe` и Python-сервер. Снята
зависимость обработки радио/USBIP от записи статуса на диск; аудиоочереди
больше не должны воспроизводить секунды накопленного PCM после паузы.
Короткие аппаратные проверки и восстановление после искусственных пауз прошли;
длительная устойчивость и системный input lag пока не подтверждены.

## Установленные причины каскада в коде

- Python синхронно записывал status JSON при **каждом** событии `radio_*`,
  обходя ограничение частоты. Запись и console flush выполнялись на том же
  asyncio loop, который обслуживает команды, аудио и подтверждения.
- Capture допускал 2048 одномиллисекундных фрагментов PCM. Переполнение
  вызывало исключение и закрывало радиосоединение целиком.
- Render URB ждали общего аудиолока без проверки возраста. Частичный PCM
  мог пережить паузу и попасть в следующий радиоблок.
- C++ IPC хранил до 128 сообщений, включая аудио; переполнение завершало
  мост. Запись статуса и проверка stop-файла выполнялись в radio tick.

Это подтверждённые свойства исходного кода, а не доказательство причины
каждого пользовательского отвала или задержки всей Windows.

## Изменения

- Python: отдельный поток диагностики, ограниченная очередь логов и только
  последний снимок статуса. Снимок формируется раз в 200 мс; ошибки диска/
  блокировка консоли не выходят в RF callback. PCM в журналы не пишется.
- C++: отдельный поток статуса/stop-файла. Ошибки записи считаются в
  `RuntimeFileIoErrors`; опрос stop-файла имеет период до 100 мс плюс время
  текущей файловой операции.
- Capture: максимум 32 USB-фрагмента; возраст проверяется перед выдачей
  и после ожидания таймера. Старый PCM отбрасывается, команда/ассоциация
  сохраняются. Запросы больше 32 ISO-слотов явно отклоняются.
- Render: бюджет свежести 64 мс от входа в backend, включая ожидание
  аудиолока/clock credit. Просроченный PCM не отправляется; ISO-слоты
  возвращаются с actual=0 и EXDEV (-18). Ложного подтверждения передачи нет.
  Отсутствие аудиочасов само по себе больше не сбрасывает радиосессию.
- Частичный render очищается при истечении возраста, UNLINK и смене аудио-
  конфигурации. Отложенный URB не может продолжить старую конфигурацию.
- C++ IPC: максимум четыре ожидающих аудиосообщения, срок 32 мс. Команды,
  события association/removal и ACK не выбрасываются ради лимита PCM.
  Частично записанный TCP-кадр обязательно дописывается, чтобы не повредить
  поток. Уже переданные TCP-байты невозможно отозвать этой очередью.

32 мс capture / 64 мс render — начальные бюджеты восстановления для наблюдавшегося радиоблока 8 мс,
а не измеренная полная задержка и не дополнительная обязательная буферизация.
Обычный поток выдаётся по существующим часам устройства. Сохранены High-Speed
USBIP presentation/bInterval=1 и ожидание фактического ACK для переданного
радиоблока. Подписи/политики безопасности Windows не менялись.

Новые проверки используют реальный loopback TCP и USBIP RET_SUBMIT:

| Возмущение | Проверяемый результат |
| --- | --- |
| Управляемые паузы 20, 50, 100, 250, 500 мс | Capture выдаёт допустимый/свежий PCM, поколение сессии не меняется |
| Настоящая блокировка asyncio на 100 мс | Старый capture отбрасывается; команды и свежий PCM продолжают проходить |
| Задержка audio ACK и восемь ожидающих render URB | Команда завершается до audio ACK; старый хвост возвращается с ISO-ошибками; новый PCM проходит |
| Джиттер и пропуск целых RF audio messages | Ожидающий capture возобновляется на свежем пакете без переподключения |
| Раздробленная доставка TCP с паузами 20–100 мс | Байты/порядок сохраняются, команда и следующий capture корректны |
| Burst 270 радиоблоков | Очереди ограничены; переполнение PCM не закрывает IPC |
| Заблокированный/недоступный статус и console | RF loop не ждёт диск, статус остаётся latest-wins |
| Частичная TCP-запись перед паузой | Оставшаяся часть кадра сохраняется; отбрасываются только целые старые audio frames |

Управляемые часы нужны для воспроизводимого решения «просрочен/свежий»;
это не утверждение о точности Windows scheduler. Отдельные тесты используют
настоящие задержки. Таймаут теста насыщения 65 URB увеличен с 1 до 5 секунд:
он проверяет лимит ресурсов, а не realtime-производительность тестового раннера.
Рабочие аудиодедлайны от этого не увеличены. Раннер выбирает тот же Windows
Selector loop, что сервер.

## Что ещё требуется на железе

Тесты не запускают kernel USBIP/UDE, штатный XboxGip, WinUSB или радиотракт.
Нужно проверить реакцию XboxGip на ISO-ошибки и отсутствие повторного импорта,
длительный full-duplex, subjective stereo и нагрузку/системные DPC отдельно.
Настоящий разрыв IPC и отрицательный USB TX ACK по-прежнему считаются
неисправностью; зависший физический USB WritePipe не устранён этим патчем.

Новые счётчики в radio-status: `CaptureDroppedFrames`, `CaptureQueueHighWater`,
`RenderExpiredRequests`, `RenderDiscardedBufferedBytes`, `RenderMaxQueueWaitMs`,
`RadioAudioMaxAckMs`, `EventLoopMaxLagMs`, `TelemetryIoErrors`,
`TelemetryDroppedEvents`. Это показатели отдельных участков, не end-to-end
latency. Первоначальный прогон следует делать только с новой гарнитурой:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Run-UsbGip.ps1 -AudioBridge -NewHeadsetOnly -FallbackOutput none -Seconds 0
```

Требуется привязка физического адаптера к WinUSB и его переподключение.
Возврат: `Run-UsbGip.ps1 -Stop`, затем `Switch-WinUSB.ps1 -Mode Restore`
из повышенного PowerShell и переподключение адаптера. Сохранённая штатная
привязка находится в `work/binding-state.json`.

## Искусственные паузы на настоящем USBIP/UDE стеке

`scripts/Test-UsbGipPause.ps1` — отдельный ручной fault experiment.
Он проверяет PID и StartTicks из текущего launcher, разрешает только
изолированный сервер новой гарнитуры без fallback. Приостанавливает только

## Бессрочный прогон

По просьбе пользователя ограничение длительности снято. `Run-UsbGip.ps1`
по умолчанию использует `-Seconds 0`, передаёт ноль Python и C++ и не имеет
своего deadline остановки. Python `--seconds 0` ждёт отмены вместо sleep(0);
C++ `run --seconds 0` уже поддерживал бессрочную работу. Убран также часовой
idle timeout локального RF IPC, чтобы выключенная гарнитура не завершала мост.
Таймауты I/O/авторизации и бюджеты свежести PCM сохраняются.

В state-файле `DurationSeconds=0`, `Unlimited=true`. Изменение длительности
активного сеанса требует остановки и нового запуска. Ручная остановка:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Run-UsbGip.ps1 -Stop
```

Новая гарнитура, бессрочный запуск:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Run-UsbGip.ps1 -AudioBridge -NewHeadsetOnly -FallbackOutput none
```

Завершения в 12:37 у нового сеанса нет. Это бессрочная работа процессов,
не автозапуск после перезагрузки и не гарантия отсутствия ошибок/отвалов.


Бессрочный сеанс запущен 2026-10-15 около 12:30, гарнитура автоматически
подключилась, Windows импортировала USBIP-порт 1. Проверены command lines
всех трёх процессов: launcher `-Seconds 0`, Python `--seconds 0`, C++
`--seconds 0`; state Unlimited=true, Error=null. Доказательство:
`work/usbip-unlimited-proof.json`. Полный Python-набор — 80 PASS, включая
реальное TCP-обслуживание в бессрочном режиме с последующей отменой и

## Восстановление старой гарнитуры и независимые аудиочасы

При неудачных попытках сопряжения в таблице оставался реально активный
геймпад: за пять секунд поступило четыре новых RF-пакета. Поэтому перебор
каналов не запускался. После полного выключения геймпада таблица стала пустой;
следующее сопряжение перешло 165 -> 1 и получило pair request и association
старой гарнитуры. Windows создала ее USBIP-устройство. Нажатия кнопки адаптера
не были потеряны; при активном клиенте адаптер не мог сканировать каналы.

Старая гарнитура одна на канале 1 тоже запиналась. За 19.711 с: RX 118.917,
TX 115.873 блока/с, expiry +88, capture drops +0, clock credit overflow +61;
максимальная физическая USB-запись в том окне 3.3 мс. Нормальный выбранный
формат требует 125 блоков/с. `work/usbip-old-alone-channel1.json`.
Это локализует недостаточный темп/пропуски, но не доказывает RF-помехи:
счётчики видят сообщения после аппаратного и программного приёмного пути.

В исходном `work/upstream-xone/driver/headset.c:gip_headset_send_samples`
воспроизведение запускается отдельным hrtimer с GIP_AUDIO_INTERVAL. В нашем
мосте каждый входящий RF audio message ошибочно использовался как отдельное
разрешение на один выходной блок; отсутствие микрофонного пакета тем самым
сокращало и воспроизведение. Для сравнения подготовлен отдельный режим:

- `usbip_reference_server.py --audio-independent-clock` требует `--audio-bridge`.
- `Run-UsbGip.ps1 -OldHeadsetIndependentClock` включает режим только для 0b17,
  сохраняя прежний режим новой 0b32 и геймпада. По умолчанию флаг выключен.
- USB capture получает начальный запас одного RF-блока (8 мс) и сохраняет темп;
  отсутствующие микрофонные фрагменты заменяются тишиной и отдельно считаются
  в CaptureConcealedFrames. Настоящий PCM по-прежнему ограничен 32 мс.
- Render получает самостоятельный темп 8 мс, без накопления RF credits.
  После паузы нет неограниченного воспроизведения всех пропущенных тиков.
- Допуск работы без свежего входящего RF ограничен 128 мс. После этого capture
  ждёт свежий RF; render использует прежние дедлайны и сообщает ISO-потери.
  Управляющий канал и ассоциация от такого пропуска не сбрасываются.
- USB TX success по-прежнему возвращается только после реального ACK моста.
- `-PairOnStart` открывает начальное окно сопряжения через существующий
  `--pair-beacon`; команда теперь работает также в run/controller-test.

85 Python-тестов и 50 C++-сценариев прошли. Новые тесты проверяют несколько
render-блоков без отдельных микрофонных credits, обязательность USB ACK,
тишину при коротком пропуске, остановку подстановки после 500 мс без RF,
возобновление настоящего PCM и сохранение управления после истечения holdover.

Аппаратный режим запущен бессрочно:
`Run-UsbGip.ps1 -AudioBridge -NativeController -OldHeadsetIndependentClock -PairOnStart -FallbackOutput none -Seconds 0`.
SHA256 xone-probe.exe:
`619ace3cde648dec040ab88d9b0af2e944958b9721f5c43daedb6ba9cc044ff2`.
Первый запуск остановился на неверно записанном --pair; имя исправлено на
--pair-beacon и проверено через read-only list до повторного запуска.

Старая подключилась автоматически уже на канале 165, expiry=0 и capture drops=0
в первом окне, очередь короче. Пользователь подтвердил чистый звук сначала
одной старой, затем обеих гарнитур одновременно с включённым геймпадом.
Это успешный короткий тест, не доказательство длительной устойчивости.
Смена канала 1 -> 165 совпала со сменой clock mode, поэтому субъективный
эффект нельзя приписать исключительно изменению часов.
Микрофонный голос в этом прогоне не прослушивался; его качество отдельно
не принято. Снимки: `work/usbip-old-independent-first-proof.json`,
`work/usbip-three-device-independent-clock.json`.

Для возврата к прежнему аудиорежиму нужен Stop и запуск без
-OldHeadsetIndependentClock; драйвер адаптера менять не требуется.
Установщик/деинсталлятор и публикация остаются незавершённой отдельной работой.

Совместное окно после подтверждения пользователя: 30.602 с, новая RX/TX
124.57/124.50 блока/с, старая 124.63/124.60; expiry=0 и capture drops=0 в обеих,
новой подстановки тишины нет. Все три Ready=true, generation=1. Скорости
рассчитаны по 500-мс status snapshots и не являются точностью аудиочасов.
У старой физический USB TX lifetime max=14.124 мс (три записи >8 мс), поэтому
редкие задержки общего USB пути остаются возможными даже при чистом окне.
Контрольный архив и SHA: `work/usbip-three-device-checkpoint.json`.
